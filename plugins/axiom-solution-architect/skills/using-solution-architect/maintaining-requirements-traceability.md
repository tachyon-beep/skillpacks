# Requirements Traceability

Optional reference: use the parts relevant to the current question and selected policy. Existing records can satisfy the evidence; no fixed artifact count, review duration or reviewer count applies.

Trace consequential requirement IDs to design decisions, implementation locations, verification and acceptance evidence. A ticket with links can be enough; an RTM is useful when several consumers need a shared baseline.

Check missing mechanisms, orphaned design/code/tests, stale references and unsupported acceptance. Preserve the distinction between a test's existence, execution result and proof that it covers the criterion.

When requirements change, revisit linked interfaces, migrations, operations and test expectations. Record owner/rationale/status for waived or deferred coverage. Version the baseline when consumers need a stable agreement.

Output: coverage/gap summary with source links and next actions, not a document count.
