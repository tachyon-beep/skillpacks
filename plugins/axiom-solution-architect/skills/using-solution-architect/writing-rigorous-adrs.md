# Architecture Decision Records

Optional reference: use the parts relevant to the current question and selected policy. Existing records can satisfy the evidence; no fixed artifact count, review duration or reviewer count applies.

Record decisions that future maintainers will need to understand: context/constraints, considered alternatives (including current state), choice, supporting evidence, consequences, reversibility and revisit trigger.

Use concrete costs and failure modes where known. Label estimates and unknowns. Explain why a plausible alternative was rejected rather than constructing straw options. A technology preference is not a requirement.

Status: proposed/accepted/superseded/rejected; include date, owner and source baseline. Post-hoc ADRs are useful when honestly labeled reconstructed; do not imply approval preceded implementation.

Small decisions can live in the issue or design note. Do not impose ADRs from file count alone. Update affected requirements, integration/recovery assumptions and prior ADR links when a material choice changes.
