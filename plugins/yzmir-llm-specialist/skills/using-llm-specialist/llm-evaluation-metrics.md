# LLM evaluation contract

Use for task-specific quality claims, model/config comparisons or a deployment gate.

- Define task outcome, independent unit, representative slices and failure costs. Select metrics because they measure the task; token overlap is not a general correctness metric.
- Keep prompt/tuning/selection data separate from reporting. Record dataset/model/prompt/tool versions and contamination provenance.
- Compare baselines under common inputs/budgets; use pairing/clustering and selection corrections appropriate to the design through counterfactual statistics.
- Check human/judge rubric clarity, disagreement, ordering/verbosity/self-preference bias and calibration against known cases. Judge confidence is not ground truth.
- Measure failures, abstentions, tool effects, cost and latency in addition to aggregate quality. Preserve negative results and uncertainty.
- Distinguish a bounded smoke check from an evaluated quality claim. State unrun checks and coverage limitations; no mandatory stage or sample count applies to every prototype.

## Deliverable

Evaluation definition plus source/run identity, observed results and uncertainty, failure slices and release/next-experiment decision. The specialized checks below are optional depth; verify current suite/provider APIs before adoption.

## Part 6: LLM-as-Judge — Current State and Pitfalls

LLM-as-judge means using a strong LLM to grade outputs from another LLM. It is now the dominant cheap-but-correlated proxy for human preference. The seminal study is Zheng et al. 2023, "Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena" (arxiv 2306.05685), which showed strong judges (then GPT-4) reach roughly 80% agreement with human pairwise preferences — about the level humans agree with each other — but also catalogued the biases below.

**Use LLM-as-judge for:**
- Pairwise preference between two model variants (which response is better?)
- Open-ended generation where reference answers are infeasible (chat, creative writing)
- Quick iteration during development before human eval

**Don't use it as the only signal for:**
- Safety-critical decisions (medical, legal, financial advice quality)
- High-stakes A/B-test go/no-go decisions (combine with human eval)
- Anything where the judge may have been trained on outputs from one of the candidates (self-preference)

### Known judge biases (and mitigations)

1. **Length / verbosity bias.** Judges (and humans) prefer longer answers even when the longer answer adds no information. Dubois et al. 2024, "Length-Controlled AlpacaEval: A Simple Way to Debias Automatic Evaluators" (arxiv 2404.04475), showed that fitting a GLM to factor out length lifts Spearman correlation with Chatbot Arena from 0.94 to 0.98. **Mitigation:** length-control your judge (LC AlpacaEval recipe), or include length as an explicit penalty in the rubric.

2. **Position bias.** In pairwise comparisons, judges prefer whichever answer is presented first (or sometimes second). **Mitigation:** evaluate each pair twice with positions swapped; take the mean. If the judge flips its verdict on swap, mark the pair as a tie.

3. **Self-preference / self-enhancement bias.** Judges tend to prefer responses generated by themselves or from the same model family. **Mitigation:** never use a judge from the same family as either candidate. For high-stakes evals, use a multi-judge ensemble across providers.

4. **Verbosity / formatting bias.** Bullet lists, headers, and confident tone are over-weighted. **Mitigation:** explicit rubric items ("ignore formatting; score on factual accuracy and helpfulness only").

5. **Refusal bias.** Some judges penalize refusals even when refusal is correct (unsafe prompt). **Mitigation:** separate safety eval from quality eval; do not blend.

### Calibration: temperature and prompt for judges

- Judges should run at **`temperature=0`** (or very low) for reproducibility. Variance in judge scores compounds with variance in candidate outputs.
- Prefer **chain-of-thought rubrics** for chat / instruct judges: ask the judge to walk through the rubric items before producing a score. (For reasoning-model judges, see [reasoning-models.md](reasoning-models.md) — don't add explicit CoT scaffolding.)
- **Anchor the scale** with concrete descriptions per score level (1 = "clearly fails the rubric", 5 = "exceeds the rubric"), not bare integers.

### Pairwise vs absolute scoring

| Mode | Use when | Pros | Cons |
|------|----------|------|------|
| **Pairwise (A vs B)** | Comparing two variants | High agreement with humans (Zheng 2023); naturally calibrated | Doesn't give absolute quality; needs N(N-1)/2 comparisons |
| **Absolute (1-5 score)** | Tracking quality over time; one variant | Cheap; one call per sample | Drifts across runs; harder to calibrate |
| **Reference-based (vs gold)** | You have reference answers | Anchors to truth | Reference quality caps eval quality |

**Recommendation:** for model selection, use pairwise with position-swap. For monitoring, use absolute with a frozen judge model and prompt.

### Multi-judge ensembles

For high-stakes evaluation, ensemble judges across providers (e.g., one frontier-general model from each of 2-3 vendors). Aggregate by majority vote (pairwise) or mean (absolute). Disagreement between judges is itself a useful signal — flag those examples for human review.

```python
def ensemble_judge(candidate_a, candidate_b, prompt, judges):
    """Pairwise judge ensemble with position swap."""
    votes = []
    for judge_fn in judges:
        # Forward order
        v1 = judge_fn(prompt, candidate_a, candidate_b)  # returns 'A', 'B', or 'tie'
        # Swapped order
        v2 = judge_fn(prompt, candidate_b, candidate_a)
        v2_unswapped = {'A': 'B', 'B': 'A', 'tie': 'tie'}[v2]
        if v1 == v2_unswapped:
            votes.append(v1)
        else:
            votes.append('tie')  # judge flipped on swap → no clear winner
    # Majority across judges
    from collections import Counter
    return Counter(votes).most_common(1)[0][0]
```


## Part 7: Behavioral and Capability Evaluation Suites

Single-task metrics (F1, ROUGE) cover narrow capabilities. For broader assessment — knowledge, reasoning, tool use, safety, agentic behavior — use established suites.

| Suite | Maintainer | Strength | When to use |
|-------|------------|----------|-------------|
| **[Inspect AI](https://github.com/UKGovernmentBEIS/inspect_ai)** | UK AI Security Institute | First-class agent / tool-use scaffolding; large eval registry (200+ in `inspect_evals`); model-graded evals | Agentic, safety-critical, or capability evaluations; you want a real framework, not just metric scripts |
| **[OLMES](https://github.com/allenai/olmes)** | Allen Institute for AI (Ai2); arxiv 2406.08446 | Reproducible, prompt-format-controlled standard; resolves cloze-vs-MCQ ambiguity | Comparing base / pretraining models on knowledge and reasoning benchmarks where prompt format silently swings results |
| **[OpenAI Evals](https://github.com/openai/evals)** | OpenAI | Easy custom evals with YAML configs; integrates with OpenAI Dashboard | OpenAI-centric stacks; private evals on proprietary data |
| **[lm-evaluation-harness](https://github.com/EleutherAI/lm-evaluation-harness)** | EleutherAI | Backend for HF Open LLM Leaderboard; widest task coverage; vLLM and HF model support | Pretraining and base-model comparison; standard reproducible numbers |

**Rule of thumb:**
- Building agents → Inspect AI
- Comparing base models → OLMES or lm-evaluation-harness
- OpenAI-only stack → OpenAI Evals
- Need hundreds of standard tasks fast → lm-evaluation-harness

These suites are scaffolds; they don't replace task-specific metrics or human eval. They give you a known reference point alongside your own metrics.


## Part 8: Evaluating Reasoning Models

Reasoning models (o-series, Claude extended thinking, DeepSeek-R1, Gemini thinking, Qwen QwQ) generate hidden or visible thinking tokens before the final answer. Standard eval pipelines under-measure them.

### Track thinking tokens separately from output tokens

```python
# Pseudo-shape; exact field names depend on the provider API
result = client.responses.create(model="<frontier-reasoning>", ...)
metrics = {
    "thinking_tokens": result.usage.reasoning_tokens,   # provider-specific field
    "output_tokens": result.usage.completion_tokens,
    "thinking_to_output_ratio": result.usage.reasoning_tokens
                                / max(1, result.usage.completion_tokens),
    "answer_correct": grade(result.output_text, gold),
}
```

Why it matters:
- **Cost.** Thinking tokens are billed; a model that takes 4× the reasoning to reach the same answer costs 4× as much for equal accuracy.
- **Latency.** Time to first answer token grows with thinking-token count.
- **Regression detection.** A model that gets the same accuracy with 2× thinking tokens has regressed even if the headline metric is stable.

### Evaluate reasoning quality, not just final answer

For domains where the *justification* matters (math proofs, legal reasoning, medical triage, code review), grade the reasoning trace as well as the final answer:

- **Step-correctness rate.** What fraction of intermediate steps are sound, given the prior steps?
- **Faithfulness.** Does the final answer follow from the stated reasoning? Use an NLI model (Part 1's `evaluate_rag_faithfulness` recipe).
- **Reasoning-rubric LLM judge.** A separate judge that scores only the chain-of-thought, not the final answer.

Note: many providers do not expose the internal chain-of-thought from reasoning models. When the trace is hidden, you're limited to grading the final answer plus inferring from token counts.

### Reasoning-mode regressions

When a vendor updates a reasoning model, watch for:
- **Reasoning-effort recalibration.** "Medium" effort on the new model may map to a different token budget than "medium" on the old one.
- **Format drift in the final answer.** New thinking patterns sometimes change how the answer is presented.
- **Tool-call regressions.** Reasoning models that also use tools can regress on tool-selection accuracy independently of pure-reasoning quality.

Always re-run your full eval suite after a reasoning-model upgrade. **For prompting and configuration of reasoning models, see [reasoning-models.md](reasoning-models.md).**


## Part 9: Red-Teaming Primer

Quality eval and safety eval are different jobs. A model can score high on MT-Bench and still fold to a five-line jailbreak. Red-teaming probes adversarial robustness — the worst-case behavior under hostile inputs.

### Two modes

**Automated red-teaming.**

- **PAIR (Prompt Automatic Iterative Refinement)** — Chao et al. 2023, "Jailbreaking Black Box Large Language Models in Twenty Queries" (arxiv 2310.08419). An attacker LLM iteratively refines a jailbreak prompt against a target LLM in fewer than ~20 queries. Black-box, semantic.
- **GCG (Greedy Coordinate Gradient)** — Zou et al. 2023, "Universal and Transferable Adversarial Attacks on Aligned Language Models" (arxiv 2307.15043). Optimizes a token-level adversarial suffix against open-weights models; the suffixes transfer to closed models. White-box origin, black-box transfer.

These give you a quantitative attack-success-rate (ASR) baseline. ASR > 0 on safety-critical prompts is a finding, not a feature.

**Human-led red-teaming.** Domain experts (security pros, policy specialists, healthcare clinicians) probe categories your automated attacks won't think of: misuse pathways, indirect harms, jurisdictional compliance, dual-use information. Cheap, slow, irreplaceable.

### Minimum viable red-team for a deployed LLM application

1. Define refusal categories (illegal, self-harm, CSAM, weapons, your domain-specific lines).
2. Build a seed prompt set per category (10-30 prompts each).
3. Run automated attacks (PAIR-style) to expand each seed by 10×.
4. Measure ASR per category against your deployed system (model + system prompt + filters).
5. Patch the highest-ASR categories (system-prompt hardening, output filters, escalation to safer model).
6. Re-run weekly; track ASR over time as a regression metric.

For the full safety / alignment / guardrails treatment, see **[llm-safety-alignment.md](llm-safety-alignment.md)** and the cross-pack **`ordis-security-architect`** for adversarial-ML threat modeling.


## Part 10: Golden-Set Discipline

The eval set determines what you can know about your system. Treat it as a versioned engineering artifact, not a folder of sample prompts.

### Per-task eval-set design

For each user-facing task (intent), build a labeled eval set with:

- **Coverage.** Every supported feature represented; every refusal category represented.
- **Stratified slices.** By user segment, language, domain, difficulty. Compute metrics per slice — aggregate scores hide segment failures.
- **Edge cases.** Empty inputs, very long inputs, malformed inputs, prompt-injection attempts, ambiguous inputs.
- **Adversarial seeds.** From your red-team output (Part 9).
- **Size.** Minimum ~200 per slice for stable metrics; 500+ if you want to detect small effects.

### Contamination checks

If your eval set leaked into training data, your metrics are fiction.

- **Exact-match check.** Hash every eval example; check provider docs / training-data audits for matches.
- **N-gram overlap.** For each eval example, compute the longest n-gram (n=13 is the typical canary length) shared with any plausible training corpus. High overlap → likely contaminated.
- **Behavioral check.** Compare model performance on your eval set vs a held-out set you constructed *after* the model's training cutoff. A large gap is a contamination signal.

```python
def detect_contamination(eval_examples, training_corpus_iter, n=13):
    """Flag eval examples that share long n-grams with training corpus."""
    contaminated = []
    eval_ngrams = {ex["id"]: extract_ngrams(ex["text"], n) for ex in eval_examples}
    for chunk in training_corpus_iter:  # stream training data
        chunk_ngrams = extract_ngrams(chunk, n)
        for ex_id, ngrams in eval_ngrams.items():
            if ngrams & chunk_ngrams:
                contaminated.append(ex_id)
    return set(contaminated)
```

### Eval-set versioning

- **Pin a version** (`eval_v1.2.3`) in every report. Metric numbers without an eval-set version are unreproducible.
- **Diff before promoting.** When you add or change examples, re-run the previous champion model; if its score moves more than your noise floor, the change is too big — split it into multiple smaller versions.
- **Hold a frozen "regression suite."** Never edit it. New examples go into a separate "growth set" that you fold into the regression suite only at major versions.
- **Separate train / val / eval / red-team.** Examples must never appear in more than one. Document the split.
